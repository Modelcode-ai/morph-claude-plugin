# ENG-10581: witness init as an agent-driven interview

Branch `eng-10581`, stacked on `eng-10580`. Package `packages/witness`.

## TL;DR

- `witness init --scan` prints the repo's facts as JSON and writes nothing. Every fact carries a
  `confidence` (`high`, `medium`, `low`) and `evidence` (`file:line`, a file or a manifest). The
  plain `witness init` still writes `.witness/witness.example.toml` as before, and its `--json`
  output now also carries `confidence` and `evidence`.
- The `init` skill is now a short interview over 7 stages. The agent asks one question at a time,
  each with a recommendation and its evidence. It never asks what the repo answers. "Use your
  defaults" skips every question. The per-stage detail lives in `skills/init/interview.md`.
- The config is the record. A one-line comment in `witness.toml` that names a project, dependency
  or variable counts as a decision. `--scan` reports what an existing config covers and what is
  `missing`, so a later `init` asks only about the gaps.
- Morph profile: the same stages. Each question becomes a blocker in the report. A rendered config
  settles stages 1 to 4.
- `check:skills` checks reference files per profile: a budget of 1500 words, the same tool-name
  check, no frontmatter, and `SKILL.md` must name each one. `skills install`, `skills path` and
  `build:plugin` already rendered every `.md` file; tests now cover the reference file.
- Self-check on eShopOnWeb: 4 questions in interactive mode. The baseline passed: functional 54,
  publicapi 143, e2e 2 passed and 1 skipped. In defaults mode nothing is asked, and the run stops
  at one blocker (`DOTNET_ROOT`, the .NET 11 SDK). Once that is set, it ends with the same
  baseline.

## The `init` skill

`skills/init/SKILL.md` (flow, rules for asking, one line per stage) and `skills/init/interview.md`
(per stage: what to look at, when the repo already settles it, the question, the default and how
to record it). `SKILL.md` tells the agent to read `interview.md` when it reaches stage 1.

Rules for asking (standalone):

- Never ask what the repo answers. A high-confidence fact that nothing contradicts settles the
  decision, and the agent says in one line what it chose.
- Otherwise ask one question: the recommendation, its evidence and the other options. Ask the
  user and wait.
- If the user says to use your defaults, at any point, ask nothing more: take every default and
  list them in the report.
- With an existing config, ask only about `config.missing`, `config.unmatched`, or what changed.

Stages:

1. Scope: which projects become suites; the excluded ones; the ones that need a filter.
2. How the app runs: a local process, Docker or compose, or an existing URL. Skipped when every
   suite hosts the app.
3. Infrastructure: compose, an existing store, or an in-memory mode.
4. Secrets, test users and test data.
5. Check until it passes. Ask only for choices the user owns: installing an SDK, a browser or a
   certificate, freeing a port, or moving the app into Docker. Installing software is never a
   default. The config is written so it works once the user has done the step, and the step is
   reported as what blocks the agent.
6. Baseline. The question is whether to keep tests that already fail as known failures (the
   default) or narrow the suite.
7. Commit. The default is not to commit; the report names the files.

Morph: "No one answers here." A rendered config settles stages 1 to 4. Otherwise a
high-confidence fact settles the decision, or the agent takes the default and records a blocker
with the question, the choice and the evidence. Anything that needs something only the user has
(a secret, a URL, a paid service) is a blocker. Stage 4 and stage 7 keep ENG-10580's morph text
(morph supplies secrets; commit the config with the tests).

The skill says "ask the user and wait for the answer" and names no tool.

### What the self-check changed in the skill

The first draft's stage 5 default, "the fix that changes least outside the repo", did not settle
the SDK case. In defaults mode it left the agent choosing between installing an SDK and a Docker
wrapper. The default now says installing software is never a default: write the config so it
works once the user has done the step, and report the step.

## Scope changes

- Added facts not in the issue's list: `containers`, `urls`, `health` routes with their service,
  `testUser`, `exampleValue` and `envName` on env names, and toolchain versions. Stage 2 needs the
  health routes and URLs, and stage 5 needs the toolchain versions.
- `init --json` (not `--scan`) now carries `confidence`, `evidence`, `project` and `filtered`.

## Open questions

- Stage 7's default is "do not commit". It is safe, but under "use your defaults" the config never
  reaches the repo. Should the default be to commit when the config holds no machine path?
- In standalone mode, the recommendation and the stated default are always the same, so "use your
  defaults" is well defined. The cost is that an agent can't recommend something different for a
  particular repo (for example, committing when the user owns it).
- The scan does not read agent instruction files (CLAUDE.md, AGENTS.md), where morph keeps its
  real start command. Reading them would help; are they trusted enough to use?
- Settings classes (pydantic `BaseSettings`, .NET options binding, Spring `@ConfigurationProperties`)
  are not scanned for env names. morph's secrets go unseen because of this.
- `AZURE_SQL_*_CONNECTION_STRING_KEY` is a medium-confidence false positive: names that hold the
  name of a secret. A rule for "`*_KEY` whose value is a key name" needs the code's data flow.
- The generated header comment ("review it, then save it as ...") stays in `witness.toml` after
  the copy. The skill doesn't say to drop it.
- Morph follow-up (not done here): once `refresh_witness.sh` passes `--profile morph`, morph's
  prompt does not need to explain the interview. The morph text in `interview.md` covers it.
