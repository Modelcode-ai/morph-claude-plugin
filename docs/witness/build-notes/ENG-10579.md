# ENG-10579: CLI apps as a test kind (desktop and mobile accepted)

Branch `eng-10579`, stacked on `eng-10574`. Package `packages/witness`.

## TL;DR

- `kind` accepts `api`, `ui`, `cli`, `desktop` and `mobile`. The kind reaches `status.json`, CTRF
  (`extra.witness.kind`), `witness status` and `witness report`; checked on the kit's `cli` run.
- The classifier knows CLI tests: a process call plus something that names the app's command
  (console script, `-m <pkg>`, package `bin`, `cmd/` binary, cargo bin, built-binary path,
  `go run`), click/typer `CliRunner` invoking the entry-point function, pytest-console-scripts,
  testscript, gexec, assert_cmd, trycmd and bats. Calling the command's functions stays a unit test.
- `init` finds bats and Cargo projects, and Android `androidTest`, Detox, XCUITest, Maestro and
  Flutter `integration_test` projects. Desktop and mobile suites get a note to model the driver or
  emulator as a `[[dependency]]` or `[[service]]`.
- New `bats` adapter. New kit project `cli-bats`: a Node CLI over the kit app, tested with bats.
  It passes all 7 scenarios; the whole kit passes (matrix below).
- Follow-ups: `status` and the markdown report show why a suite was skipped; `init` comments out a
  service no proposed suite uses; the dotnet preset turns off the MSBuild server, node reuse and the
  compiler servers for every dotnet suite.
- `docs/witness/APP-KINDS.md`: what counts per kind, how to model it today, what is missing.

## What changed

**Config (`src/config.ts`).** `KINDS = api, ui, cli, desktop, mobile`. `KIND_HELP` describes each
one; an unknown value fails with `expected one of "api", "ui", "cli", "desktop", "mobile"`.

**Classifier (`src/functional.ts`).**
- New signal types `exec`, `cli`, `desktop`, `mobile`.
- `projectEntries(root, dir)` reads the app's command-line entry points from the manifests in the
  project folder and its parents: `pyproject.toml` scripts and name, `setup.cfg`/`setup.py`
  console scripts, `__main__.py` packages, `package.json` `bin`, `go.mod` and `cmd/*`, `Cargo.toml`
  package and `[[bin]]`, the `pom.xml` artifactId, files in `bin/`.
- A file with an `exec` signal is `cli` when one of its string literals names an entry point or a
  built binary (table in APP-KINDS.md). bats files are read line by line: a command that is a path,
  a variable, a known name, or any bare name after `PATH` changed in the file or a file it `load`s.
- New languages for the classifier only: Rust, bats, Swift, Dart (masked as Go, Ruby, Go and JS).
- Kind order when a project mixes kinds: desktop, mobile, ui, api, cli. A file that runs the
  command and also sends HTTP requests is `api`.
- `cli` projects count as hosting the app, so `init` writes `service = []`.
- `check` warns about CLI suites too; its text now lists all the ways a test can drive the app.

**`init` (`src/init.ts`).**
- Projects: `.bats` files (`bats` adapter, `npx bats` when a package.json has bats), `Cargo.toml`
  (generic, `cargo test --test <file>` for a mixed crate, a note that there is no JUnit), Android
  `src/androidTest` (`./gradlew connectedAndroidTest`, report glob for connected results), Detox
  (`npx detox test`, its folder taken out of the plain jest project), `*UITests` (`xcodebuild`),
  Maestro flows, Flutter `integration_test`.
- Desktop and mobile suites get no `service = []` and a comment about the driver or emulator.
- A service that no proposed suite uses is written commented out with
  `commented out: every proposed suite starts the app itself, so nothing uses it` (or `no suite is
  proposed`).

**Adapters (`src/adapters.ts`).**
- `env` on a preset: set for every run, rerun, listing and plugin probe; the suite's `env` wins.
- dotnet: `DOTNET_CLI_USE_MSBUILD_SERVER=0`, `MSBUILDDISABLENODEREUSE=1`, `UseSharedCompilation=false`,
  `UseRazorBuildServer=false`. The first three are the ones `eval/eshoponweb/witness/dotnet-host`
  sets; the Razor one is harmless on SDKs that no longer use the Razor server.
- `bats`: `--report-formatter junit --output <dir>`, selection `--filter '^(name|...)$'`,
  `perTestTimeoutEnv` sets `BATS_TEST_TIMEOUT`. bats's "`cmd' failed due to timeout" makes the row
  `failed`/`timeout`. No native listing: last report.

**Status and report (`src/commands.ts`).** A skipped suite shows its note:
`fake  api  skipped  0 passed, ... · not run: service api ready_timeout` and, in markdown,
`| skipped: not run: service api ready_timeout |`.

**Kit.** `conformance/projects/cli-bats`: `cli/kit-items` (a Node CLI reading
`$WITNESS_APP_URL`; `bin/` would be ignored by the kit's `.gitignore`), `test/items.bats` with the
four kit tests, bats 1.13.0 from npm. `Framework.kind` replaces the playwright special case in the
kit's config. CI matrix gains `cli-bats`.

**Skills.** One sentence each in `init`, `plan`, `test-change`, `write`. Word counts: init 800,
plan 718, test-change 704, write 799. Plugin copies regenerated.

## Scope changes

- **`bats` adapter.** The brief allowed bats through the generic adapter. Generic can't select bats
  tests (the ids are `file.bats#name` and `--filter` wants the name), so the kit's select, missing,
  broken and timeout scenarios would have failed. The preset is 10 lines.
- **Adapter `env` and `perTestTimeoutEnv`.** Needed for the dotnet build-server variables and for
  bats, which takes its timeout only from `BATS_TEST_TIMEOUT`.
- **No `cargo test` adapter.** JSON output is nightly-only and cargo2junit is another install;
  APP-KINDS.md shows cargo-nextest's JUnit with the generic adapter.
- **Extra init projects** for desktop and mobile (androidTest, Detox, XCUITest, Maestro, Flutter).
  Their commands are starting points and have not run under witness.
- **dotnet env on suites only.** Service `setup` commands such as `dotnet build` still use the
  build servers; they exit normally, so the leftover servers don't stall a suite.

## Open questions

1. Should a `cli` suite default to `service = []`? It is right for most CLIs, wrong for a CLI that
   is a client of a service (like the kit's). `init` can't tell them apart.
2. XCUITest is assumed iOS (`mobile`). macOS UI tests are `desktop`; reading `SDKROOT` from the
   `.pbxproj` would decide it.
3. A `node --test` preset: common for Node CLIs, and its JUnit reporter is built in. Worth adding?
4. Desktop and mobile need a way to build the app once for several suites without a long-running
   `[[service]]`; a `[[build]]` step or a service with no `start` would do.
5. The Detox command `npx detox test` gets jest's `--json --outputFile` appended; Detox should pass
   them through, but this is unverified.
